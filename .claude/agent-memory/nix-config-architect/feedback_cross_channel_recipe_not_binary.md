---
name: cross-channel-recipe-not-binary
description: When pulling unstable-only kernel modules/GStreamer plugins into a stable-channel host, build recipes against stable pkgs rather than importing unstable's prebuilt binaries
metadata:
  type: feedback
---

When a feature needs packages that only exist on `nixpkgs-unstable` (new NixOS module + packages not yet backported to the stable channel this repo tracks), and those packages must coexist at runtime with other packages built from the stable channel - e.g. a GStreamer plugin that will be dlopen'd into a GStreamer core process, or a kernel module that must link against a specific kernelPackages set - **do not** just reference `pkgs-unstable.<attr>` (the simple pattern used in `hosts/nixos-laptop/local-packages.nix` for standalone user packages). Instead:

1. `callPackage "${inputs.nixpkgs-unstable}/pkgs/.../package.nix" { }` against the STABLE `pkgs` (or the host's own `kernelPackages` via `.extend`), sourcing only the *recipe* (a source-tree path) from the unstable flake input, not its built `legacyPackages` output.
2. This keeps everything that gets loaded together (GStreamer core + plugin, kernel + out-of-tree module) compiled against one consistent channel/ABI.

**Why:** the simple `pkgs-unstable.<attr>` pattern is fine for isolated user-facing apps (local-packages.nix's whole point) where nothing else in the process cares what channel built it. But a GStreamer plugin loaded into a stable-built `gst-launch`/relay daemon, or a kernel module loaded into a specific kernel, has a real ABI contract with its host process - mixing channels there risks a silent "plugin failed to load" or (for a kernel module) build/insmod failure from divergent internal APIs. `lib.makeExtensible`-based kernel package sets support `.extend`, and `lib.makeScope`-based package sets (like `gst_all_1`) support `.overrideScope` - both let you re-derive a new package inside the *existing* scope rather than importing a foreign one, so the recipe compiles against exactly the same core libs everything else in that scope already uses.

**How to apply:** any time a `krit.services.laptop.*`-style host-scoped module needs an unstable-only NixOS module (imported via `nixos.always.imports = [ "${inputs.nixpkgs-unstable}/nixos/modules/.../foo.nix" ]`) whose `config` block references `pkgs.<attr>` or `config.boot.kernelPackages.<attr>` for packages not in the stable channel - first check via [[nix-package-researcher]]-style lookups whether those attrs are plain source recipes (no unstable-specific deps) suitable for `callPackage`-ing against stable `pkgs`/`kernelPackages`, before defaulting to a `pkgs-unstable.legacyPackages` overlay. Concrete worked example: `hosts/nixos-laptop/camera.nix` (Intel IPU7 webcam support - `ipu7-drivers` kernel module extended onto the host's own `linux_testing` kernelPackages via `.extend`, `icamerasrc-ipu75xa` GStreamer plugin built inside the stable `gst_all_1.overrideScope`, both `callPackage`d from nixpkgs-unstable source paths - verified via real non-dry builds, all green 2026-09-25).

For extending `boot.kernelPackages` from a host-scoped module without touching `modules/nixos/toplevel/kernel.nix`: assign `boot.kernelPackages = lib.mkForce (pkgs.linuxKernel.packages.<name>.extend (kfinal: kprev: { ... }))` - reference the SAME base kernelPackages kernel.nix already selects (duplicated by name, not read back via `config.boot.kernelPackages`, which would be circular), and `mkForce` to win over kernel.nix's plain-priority assignment without editing kernel.nix itself.
