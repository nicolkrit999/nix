# Single Secret Service provider (gnome-keyring)

Exactly one `org.freedesktop.secrets` provider runs in every session: gnome-keyring, unlocked by PAM `--login` (login, sddm). In the guest, sddm-autologin starts the keyring but it stays locked: autologin has no password to unlock it. Two providers would race for the bus name and split secrets between stores.

- **kwalletd6 is a frontend, not a store.** In KWallet 6.x it wraps the Secret Service (libsecret, `org.qt.keychain`). `kde.nix` keeps `[Wallet] Enabled=true` so KIO, plasma-nm and QtKeychain apps work under Plasma, and sets `[KSecretD] Enabled=false` so the KDE store never runs. Do not stub `org.kde.kwalletd6`; if it turns out to need ksecretd, set `[Wallet] Enabled=false` and stub it instead.
- **ksecretd entry points are stubbed** in `home-nixos.nix` (`org.kde.secretservicecompat`, `org.freedesktop.impl.portal.desktop.kwallet`, `org.kde.kwalletd`). `org.kde.kwalletd5` and kwalletd6 are not stubbed: kwallet 6.30 ships `org.kde.kwalletd5.service` as `Exec=kwalletd6`, the frontend into gnome-keyring. The `org.kde.kwalletd` stub is a guard only (no package ships that name). `plasma-kwallet-pam.service` is masked and `pam_kwallet_init.desktop` hidden; PAM kwallet is forced off in `common-configuration-nixos.nix`.
- **kwallet, kwallet-pam and kwalletmanager cannot be excluded** from plasma6 (`environment.plasma6.excludePackages` is ignored for them); mask or hide the pieces instead.
- **No second gnome-keyring daemon.** The former HM `services.gnome-keyring` unit (`programs.gnome-keyring`, `modules/nixos/programs/gnome-keyring.nix`) was removed. It ran a daemon without `--login` next to the PAM one, and its ssh component is dead in gnome-keyring 50.
- **Secret portal.** `xdg-portal.nix` sets `org.freedesktop.impl.portal.Secret = [ "gnome-keyring" ]` in every portal config and installs a manifest-only `gnome-keyring.portal`, so the home-manager share carries a `gnome-keyring.portal` too. Routing is by config name (`UseIn=` is not consulted), so it is unaffected by which copy of that file wins. The full gnome-keyring package is deliberately not added to the module's own portal packages: its non-setcap `org.freedesktop.secrets.service` would shadow the system one. See also `xdg-desktop-portal-nixos.md`.
- **One SSH agent.** gcr-ssh-agent only (`services.gnome.gcr-ssh-agent`); `SSH_AUTH_SOCK` falls back to `$XDG_RUNTIME_DIR/gcr/ssh` via `environment.extraInit`. gpg-agent has `enableSSHSupport = false`, otherwise both sockets race in the systemd user environment.
- **Chromium/Electron password store.** Without a flag the backend follows `XDG_CURRENT_DESKTOP` (kwallet6 on KDE, libsecret on GNOME), splitting safe-storage keys per session. `libsecret-pinning.nix` pins brave, chromium, google-chrome and vscode via `commandLineArgs`, and wraps signal-desktop, vesktop, teams-for-linux, proton-pass, drawio, xmind, whatsapp-electron, github-desktop and insomnia (overlay; neither github-desktop nor insomnia takes `commandLineArgs`, so they use the same wrapper, insomnia being an AppImage wrapper that forwards args to Electron), claude-desktop-fhs and antigravity (`pkgs.passwordStoreWrap`). helium uses `programs.helium.extraFlags`. `~/.vscode/argv.json` is VS Code-managed and must say `"password-store": "gnome-libsecret"` (user step).
- **Guest.** The guest keyring is started but stays locked, since autologin supplies no password. The guest therefore gets one "choose a password for the new keyring" prompt per boot (a blank password leaves it unlocked for that session). Pre-seeding an empty keyring on the guest's tmpfs home would avoid the prompt but is not implemented.
- **Adding a new Electron/Chromium app:** add it to the overlay in `libsecret-pinning.nix`, or it falls back to desktop-dependent detection.
