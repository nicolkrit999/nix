# The ryoku specialization: open risks and how to test it

`specializations.ryoku` boots the upstream [Ryoku](https://github.com/Ryoku-dev/Ryoku-on-NixOS) desktop as the dedicated user `<user>-ryoku`. It builds and evaluates on both hosts and is covered by `test-spec-ryoku`, but it has **never been booted**. Everything below is unverified until a live session confirms it. Feature description: [`features.md`](../../features.md).

## Open risks

- **Materializer vs Home Manager symlinks.** Ryoku's `materialize` step writes into `~/.config` (hypr, niri `config.kdl` + `autostart.kdl` on every run, quickshell, matugen, kitty, fish, nvim, yazi, fastfetch, gtk, qt6ct, btop, starship, wireplumber). Home Manager links some of the same paths from the store; the spec therefore only places personal config in late-loaded `user.*` files and seeds that Ryoku leaves alone (see below). How the upstream CLI treats store symlinks was not readable (the CLI is not in the downloaded source). Ryoku also asserts that Home Manager does not declare `~/.config/ryoku`. Fallback if it clobbers or fails: first run backs up to `~/.local/state/ryoku/nix/backups`; move our configs to paths Ryoku does not write, or install them as writable copies.
- **Mango is not supported and was removed from the entry.** The Ryoku NixOS port supports only Hyprland and niri (its web page lists "Hyprland · niri"; Mango is compatible only with the Ryoku package, not this port), and the `ryoku-mango` session refused to start when the entry was booted on the laptop. Ryoku's module adds its mango session to `services.displayManager.sessionPackages` unconditionally, so `modules/nixos/specializations/ryoku.nix` overrides `services.displayManager.sessionData` (`mkForce`) in the spec, recomputing `desktops`, `sessionNames` and `autologinSession` from `sessionPackages` minus the package providing `ryoku-mango` (`sessionPackages` itself cannot be filtered: reading its own definitions recurses). Ryoku still installs its mango packages in `systemPackages`. The base entry's Mango is untouched.
- **Mesa vs laptop media stack.** Ryoku `mkForce`s `hardware.graphics.package`/`package32` to the mesa of its pinned nixpkgs (2026-08-23), system-wide in the entry. The laptop additionally installs `intel-media-driver` / `intel-compute-runtime` from the current nixpkgs (`hosts/nixos-laptop/system.nix`), so an ABI mix is possible (VA-API, OpenCL, camera paths).
- **Local builds and cache.** Patched quickshell and niri, a Hyprland override and the old mesa are built locally by design; only `ryotunes.cachix.org` is a cache for them and coverage of the old pin on cache.nixos.org is unverified. Expect a long first build on `nh os switch`. Never `follows` Ryoku's pinned package nixpkgs: only `inputs.nixpkgs.follows` is set.
- **Session startup.** Unverified: that `niri-session` reaches `graphical-session.target`, that `ryoku-hyprland-session` (no uwsm) starts cleanly next to this repo's Hyprland pieces being off, and that Hyprland picks the `.conf` Ryoku writes rather than a `.lua` file.
- **Shared `/var/lib/ryoku`.** Network config and the SDDM theme payload live there for every boot entry. It is persisted on impermanence hosts, so state from one entry can surface in another.
- **`hermesAgent` lock subtree.** The Ryoku input pulls an unused `hermesAgent` input (home-manager, flake-parts, uv2nix) and 4 extra nixpkgs revisions into `flake.lock`; those revisions are not on `follows` and add lock and fetch size.
- **Our keybinds (`user.*`).** `hl.unbind` before each `hl.bind` in `hypr/user.lua` is unverified: if it is a no-op for chords registered through Ryoku's rebind wrapper, both handlers fire. niri has no unbind, a clashing chord relies on last-wins across includes.
- **Hub rewriting `user.*`.** Research says the Hub never writes `hypr/user.lua`, `niri/user.kdl`, `kitty/user.conf` or `fish/user.fish`, but this was not seen live (the home is not readable from the base user). The files are Home Manager links with `force`; if materialize or the Hub replaces them, binds and personal shell/kitty config silently disappear.
- **Declared settings pickup.** `ryoku-settings-seed` runs between `ryoku-materialize` and `ryoku-shell`; whether the shell and Hub read a freshly merged `desktop.json` on the very first login (versus a later one) is unverified. In `seed-once` mode a GUI edit of a declared key survives until the declaration changes. Monitors are not declared: set them once in the Ryoku GUI. The layout persists in the Ryoku user's `/home` (`~/.config/ryoku/monitors-applied.json`), and `ryoku-monitor` regenerates `hypr/monitors.lua` from the last applied layout by hardware id at login; that recall is not verified live.
- **Fastfetch emblem seed.** `ryoku-fastfetch-emblem-seed` runs `ryoku-hub fastfetch import-logo <store png>` (only copies to `~/.config/fastfetch/ryoku-logo.png` and prints the path), then repoints `config.jsonc` via `fastfetch get | jq | save` (kind `image`, dither off), like the Hub GUI's `applyFastfetchEmblem`. Unverified live: that the Hub binary works headless that way, and that the logo renders (the type stays what `config.jsonc` has; kitty-direct needs kitty or ghostty). The sentinel is written only on full success, failures exit 0 and retry next login. The default emblem showing nothing on the laptop is a separate open question, not claimed fixed.
- **SDDM cursor (UNVERIFIED until booted).** On the laptop the Ryoku entry showed no mouse cursor in SDDM. Hypothesis: Ryoku's NixOS module wires no `CompositorCommand`, so the nixpkgs default applies (weston kiosk in the spec; the base host uses kwin via sddm-astronaut); nixpkgs sets `Theme.CursorTheme = breeze_cursors` only for the `breeze` theme and the spec has no KDE; `XCURSOR_PATH` is only set in PAM session variables (`nixos/modules/config/xdg/icons.nix`) and never reaches the greeter, so the greeter had no cursor theme to load. Change: `sddmCursorTheme`/`sddmCursorPackage`/`sddmCursorSize` (null = untouched; krit layer: Bibata-Modern-Ice, `pkgs.bibata-cursors`, 24) set `Theme.CursorTheme`/`CursorSize` and `General.GreeterEnvironment` (`XCURSOR_PATH=/run/current-system/sw/share/icons`, plus `QT_WAYLAND_SHELL_INTEGRATION=layer-shell` when the compositor is kwin) and install the package. Second round: a live boot showed the settings applied but still no cursor. Refined hypothesis (unverified until booted): the greeter runs on nixpkgs' weston kiosk, which draws no pointer and learns the cursor theme only from `[shell] cursor-theme/cursor-size` in weston.ini plus `XCURSOR_*` in weston's own environment. With the weston compositor (the nixpkgs default kiosk) it also `mkForce`s `services.displayManager.sddm.wayland.compositorCommand` to `env XCURSOR_PATH=/run/current-system/sw/share/icons XCURSOR_THEME=<theme> XCURSOR_SIZE=<size> <nixpkgs' weston> --shell=kiosk -c <weston.ini>`, with a regenerated weston.ini (nixpkgs' `[libinput]` and `[keyboard]` sections plus `[shell] cursor-theme`/`cursor-size`), because the kiosk shell draws no pointer of its own and weston learns the theme only from that block and its own environment (the greeter environment reaches only the greeter; Ryoku's greeter script, issue #191, documents this). The journal showed the first greeter attempt crashing (sddm-helper exit code 1) and then restarting fine; cause not investigated (possibly weston/greeter starting before theme or cursor resources were ready): watch whether it repeats.
- **Values derived from constants.** Default apps (`desktop.json` `desktop.apps`: browser, terminal, editor, files, notes), the keyboard (`desktop.input`: first entry of `constants.keyboardLayout`/`keyboardVariant`, no group toggle, natural scroll off) and the matugen polarity (`matugen.json` `mode`, shell and Ryogami `matugen.mode`, from `constants.theme.polarity`) are `mkDefault`/derived values, so a host or layer can override them. All of this is applied by `ryoku-settings-seed`, so the pickup question above applies to them too. A declared static theme (Dracula) of the wrong polarity fails an assertion; the wallpaper stays free. The launcher hero image path is built from the entry user's home (`specializations.ryoku.home`) and relies on Ryoku's materializer having seeded `~/Pictures/Wallpapers` first (unverified live). In `seed-once` mode, existing stores are overwritten once when the declaration changes.
- **Off on purpose.** `borg-backup` (desktop and laptop) and `wallpapersLink` are forced off in the entry; stylix runs in a reduced form (on: bat, blender, cava, fzf, gdu, gedit, lazygit, nixcord, tmux, zathura, zen-browser; off: gtk, hyprland, kde, kitty, starship, swaync, yazi; everything else off through `autoEnable = false`).
- **kitty font.** Our kitty content loads last from `user.conf`, so our font settings override Ryoku's `current-font.conf`; font changes from the Ryoku GUI will not show in kitty.
- **`YAZI_CONFIG_HOME` delivery.** Set through Home Manager session variables, `environment.d` and NixOS `environment.sessionVariables`; whether it reaches terminals started from Ryoku's launcher (and fish in tmux) is unverified. Ryoku's own `~/.config/yazi` stays untouched.
- **`ryoku update` is disabled.** `updateFlake = /var/empty`, so the Hub updater fails on purpose (it would run `nix flake update ryoku` against the flake). Update the input here with `nix flake update ryoku`.
- **Portal config `mkForce`.** Ryoku sets `xdg.portal.config.{hyprland,niri}` as lists that concatenate with this repo's, duplicating entries (for example `[ hyprland gtk hyprland gtk ]`) and breaking the single-Secret-Service and HM-equals-system routing guarantees. The spec forces `xdg.portal.config` to the shared table in `modules/nixos/toplevel/xdg-portal-config.nix`. If Ryoku's upstream routing changes, `test-portal-routing` (case `ryoku`) is the drift detector.
- **Fastfetch greeting in multiplexers.** Ryoku's `ryoku-fastfetch` wrapper takes its chafa branch when `KITTY_WINDOW_ID` is empty and `TERM=xterm-256color` (herdr, tmux), and new panes hang on the greeting. The krit layer installs a shell-independent wrapper executable `ryoku-fastfetch` (`pkgs.writeShellScriptBin` in the spec user's HM `home.packages`) that wins over Ryoku's in PATH (`/etc/profiles/per-user/<user>` precedes `/run/current-system/sw` with `home-manager.useUserPackages`), so the bash, zsh and fish greetings (all call `ryoku-fastfetch` by name) use it; it execs the real script by absolute store path (`<ryoku-desktop-data>/bin/ryoku-fastfetch`, no recursion) with the normal arguments in a plain kitty or ghostty window (`KITTY_WINDOW_ID` set, or `TERM` xterm-kitty/xterm-ghostty, or `TERM_PROGRAM` ghostty, and `TMUX` empty) and with `--logo-type none` appended otherwise. It only stops the autostart from hanging in non-kitty terminals; the GUI owns the fastfetch config and emblem (the hawk is no longer declared: pick HAWK in the Hub Fastfetch page). OPEN, unexplained: in real kitty the hawk reportedly disappears right after showing (unverified suspects: kitty-direct image cleared by the next prompt/redraw, starship/zoxide init output, a screen clear).
- **krit user units in the Ryoku user.** `agent-floor` and the Agent Reach tooling (`xiaohongshu-mcp`) stay active for `<user>-ryoku` on purpose. Other krit Home Manager units not on the personal layer's off list also run there, in a fresh home: check `systemctl --user --failed`.
- **Private dotfiles clone.** The user oneshot `ryoku-dotfiles-private-sync` clones `ssh://git@gitea-ssh.nicolkrit.ch:2222/krit/dotfiles-private.git` into `~/dotfiles-private` (SSH key `~/.ssh/id_github` from sops `github_general_ssh_key`, `IdentitiesOnly`, pinned Gitea ed25519 host key (`giteaHostKey` of `ssh-config.nix`), `StrictHostKeyChecking=yes`, `GIT_TERMINAL_PROMPT=0`; retries every 30 s, no start limit). The repository is on Gitea (user-confirmed), SSH port 2222; `GIT_SSH_COMMAND` carries the key so the unit is independent of ssh_config, and the entry's ssh-config module (`Host gitea-ssh.nicolkrit.ch`, Port 2222, `~/.ssh/id_github`, known host) makes a plain `git push` work from the clone. The HM links of `services.external.dotfiles-private` and `services.external.dotfiles` are verified present in the krit-ryoku `home.file`; the `~/.claude` links dangle until the clone exists, which the unit resolves. Existing checkout: fetch, then `merge --ff-only` only when `git status --porcelain` is empty and HEAD has no unpushed commits, else nothing (never reset or discard, Claude writes memory through these links); a non-git directory exits 1 untouched. The clone is a SEPARATE working copy from the base user's: commit and push from the Ryoku clone and pull in the other user (the unit pulls fast-forward only when clean and fully pushed). Unverified live.

## Test after booting the entry

1. Pick the `ryoku` entry; the SDDM theme is Ryoku's and the account is `<user>-ryoku` (same password as the base user).
2. Log into Hyprland: the Ryoku shell, bar and notifications appear; `systemctl --user status ryoku-shell ryoku-session.target`.
3. Log out and into niri; check the same units and that `graphical-session.target` is active.
4. `journalctl --user -b -p err` and `systemctl --user --failed`: look for materializer errors, agent-floor/xiaohongshu-mcp failures, polkit and portal errors.
5. `ls -l ~/.config/hypr ~/.config/niri ~/.config/nvim ~/.config/kitty ~/.config/fish`: are they Ryoku-written files or Home Manager store links; `user.lua`, `user.kdl`, `user.conf`, `user.fish` must exist and survive a Hub change.
6. Day-to-day stack: your terminal, browser, file manager and mime defaults open correctly (`xdg-mime query default text/plain`), neovim starts, git works; `ll`/`la` show the eza aliases in fish; `echo $YAZI_CONFIG_HOME` then `yazi` uses our config (openers, plugins, keymap).
6a. Keybinds: our chords work on Hyprland (check there is no double firing from Ryoku's handler on a clashing chord), and niri; media keys use Ryoku's OSD.
6b. Settings: `systemctl --user status ryoku-settings-seed`, `jq . ~/.config/ryoku/desktop.json` shows the declared values; set monitors in the Ryoku GUI.
6a1. Default apps: Super+B (browser) and Super+O (notes) launch the constants' apps with no "No app set" notification; Super+Return (terminal), Super+E (files) and the editor bind work too.
6a2. Polarity: set a bright wallpaper from the Ryoku picker; the palette stays dark (matches `constants.theme.polarity`).
6a3. Keyboard: `us` with the `alt-intl` variant in the shell and in every compositor session (type an accented character with a dead key).
6a4. Monitors: arrange them in the Ryoku GUI, reboot into the entry, the layout is restored.
6b1. Fastfetch emblem: `systemctl --user status ryoku-fastfetch-emblem-seed`, `ls -l ~/.config/fastfetch/ryoku-logo.png`, only relevant when `fastfetchEmblem` is declared (the krit layer leaves it null, so the unit does not exist there and the emblem is chosen in the Hub).
6c. SDDM shows the Ryoku theme (not a blank/fallback one) after boot; `systemctl status ryoku-sddm-theme-seed` on impermanence hosts.
6c1. SDDM cursor: a mouse cursor is visible on the laptop greeter (Bibata-Modern-Ice; weston kiosk with the generated weston.ini); `journalctl -b -u display-manager` shows no repeated sddm-helper exit code 1 crash/restart.
6c2. Fastfetch greeting: a new herdr/tmux pane opens instantly (no hang, no logo); a plain kitty window shows the Hub-chosen logo; `type ryoku-fastfetch` resolves to the wrapper in the Nix profile (bash, zsh and fish). Open: does the logo stay visible in kitty or vanish after showing (suspects in the possibilities entry)?
6d1. Private dotfiles: `systemctl --user status ryoku-dotfiles-private-sync` is active (exited), `~/dotfiles-private` is cloned, `ls -l ~/.claude` links resolve, fish aliases (`.custom.fish`) and nvim work.
6d. dconf and gsettings tools work (`dconf dump /`); fwupd is available.
7. Secret service: `busctl --user list | grep Secret` shows one provider (gnome-keyring); `ssh-add -l` works.
8. Graphics: `vainfo`, `glxinfo -B`, a video playback and (laptop) the camera, to catch the mesa mix.
9. Reboot into the base entry: your normal session is unchanged and `/var/lib/ryoku` state did not leak into it.

## Removing the specialization

1. Delete `specializations.ryoku.enable = true` from `hosts/nixos-desktop/default.nix` and `hosts/nixos-laptop/default.nix` (or set it `false`) to drop the entry; this alone removes it from the boot menu and from the build.
2. To remove it entirely, delete `modules/nixos/specializations/ryoku.nix`, `modules/nixos/specializations/ryoku-binds.nix`, (keep `binds-lib/`: the Hyprland, niri and Mango bind modules of the base entry use it), `modules/nixos/toplevel/xdg-portal-config.nix` (and restore the inline `portalConfig` in `xdg-portal.nix`, plus the `baseExclude` line in `flake.nix`), `users/krit/nixos/specializations/ryoku.nix` and `templates/tests/nixos/test-spec-ryoku`, then revert the Ryoku sections of the spec-contract, secret-service and portal-routing tests and their docs.
3. Drop the `ryoku` input from `flake.nix` and `nix flake lock` to prune its lock subtree (`hermesAgent` included).
3a. Drop `specializations.ryoku.settings` from the host files.
4. On the machine, `/var/lib/ryoku` and the home `/home/<user>-ryoku` stay until deleted by hand.
